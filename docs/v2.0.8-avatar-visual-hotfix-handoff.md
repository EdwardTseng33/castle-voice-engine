# v2.0.8 Avatar Visual Hotfix Handoff

Date: 2026-05-25
Owner: Howl
Branch observed: `v0.10/phase2-livekit-integration`

## Problem

Edward reported that when Sophie speaks, the avatar area sometimes becomes a full orange panel. That means the video layer disappears and only the `.stage-canvas` background remains. This is a visual-layer failure, not proof that the lipsync model or backend failed.

The active branch had returned to a single-video path:

- `#liveVideo` was both idle and speaking owner.
- Broad audio event fallback could start/stop speaking from non-final audio event names.
- Speaking/idle transitions depended on state flags instead of an independently verifiable visual layer.

## Fix

Implemented a two-layer visual path:

- Bottom layer: `#liveVideo` keeps idle video alive.
- Top layer: `#liveVideoSpeaking` preloads `/static/sophie-speaking.mp4`.
- Speaking state only toggles `liveVideoSpeaking.is-visible`; it no longer swaps the main video `src`.
- `AnimationPool(videoEl, speakingVideoEl)` now owns the speaking overlay.
- Broad audio fallback is disabled; exact output audio events drive speaking:
  - `response.audio.delta`
  - `response.output_audio.delta`
  - `response.audio.done`
  - `response.output_audio.done`
- `audio.done` now delays visual stop by 650ms to avoid sentence-tail flicker.
- Video keepalive now checks both idle and speaking videos.
- `visual_test=1` query mode added for deterministic UI verification without OpenAI audio or mic.

## Next Debug Boundary

If `visual_test=1` works but real conversation still does not show speaking motion, the visual layer is not the blocker. Check the realtime event chain:

1. Does the browser receive `response.audio.delta` or `response.output_audio.delta`?
2. Is `animPool.startSpeaking()` called once per Sophie response?
3. Does `audio.done` arrive too early or multiple times?
4. Does LiveKit integration bypass the old OpenAI datachannel event handler?

Do not fix this by reintroducing main-video `src` swaps. That path caused the orange-panel failure.

## v2.0.9 Update - 2026-05-25

Edward reported three live symptoms:

- Avatar stays in idle.
- Client camera appears not connected to Sophie.
- Voice response works, but no mouth/speaking motion.

Follow-up patch:

- Added audio-analyser driven visual fallback. If remote audio has real amplitude, `AnimationPool` calls `startSpeaking()` even if OpenAI event names do not match.
- Added transcript-delta fallback. If `response.audio_transcript.delta` or `response.output_audio_transcript.delta` arrives before audio delta, Sophie enters speaking visual state.
- Added `response.done` delayed stop fallback, so speaking can recover even if audio done is absent.
- Added client camera diagnostics:
  - logs `user media tracks audio=X video=Y`
  - logs local camera track active state
  - includes `client_camera_active` and `client_camera_tracks` in `/perception/update`

Important camera boundary:

The current browser still does not send the client video track to any real vision consumer. The old `/camera/enable` path opens server-side camera logic, which is not Edward's browser webcam on Modal. v2.0.9 only proves whether the browser camera track exists and reports that state. True "Sophie can see Edward" still needs a browser-frame upload path, LiveKit video subscription, or an OpenAI vision input bridge.

## v2.0.10 Update - 2026-05-25

Edward confirmed a partial win: Sophie now starts with speaking motion, but long replies only animate for 1-2 seconds and then fall back to idle for the rest of the sentence.

Patch:

- Added `extendSpeakingHold(ms, reason)` in `index.html`.
- Added `scheduleSpeakingStop(reason, delayMs)` so early `audio.done`, `response.done`, or broad stop paths respect the hold window.
- Audio delta now extends speaking hold by 12 seconds.
- Transcript delta now extends speaking hold by 9-12 seconds.
- Response-created clears stale hold/timers.
- `AnimationPool` audio analyser stop now waits at least 1.8s of low amplitude and also respects `window.__sophieSpeakingHoldUntil`.

Expected behavior:

- A 10-second Sophie reply should stay in speaking visual state through the sentence instead of dropping to idle after 1-2 seconds.
- This is still speaking-loop motion, not true phoneme-level lipsync.

## v2.0.17 Update - 2026-05-25

Edward reported the current mouth motion became laggy and still did not look like long-form mouth movement.

Clarification:

- The current visible mouth motion is not a realtime lipsync model.
- It is the pre-existing `/static/sophie-speaking.mp4` speaking loop shown as an overlay above idle.
- MuseTalk / LatentSync / generated mouth-model output is not driving the live UI in this path.

Patch:

- Fixed `attachAudioAnalyser()`: `_startBreathLoop()` had been swallowed into a line comment in one merged version, so the audio-driven speaking fallback was not reliably running.
- Speaking mode now pauses the bottom idle video after the speaking overlay is visible. This reduces two simultaneous 1080p video decoders during Sophie speech.
- When speaking stops, idle resumes first and the speaking overlay fades out, avoiding orange/blank frames.
- Default performance mode now prevents the audio analyser from writing CSS `transform/filter` every frame. The analyser stays responsible for detecting speech, not for visual effects.

Expected behavior:

- Lower Chrome/GPU pressure during Sophie speech.
- More stable long speaking animation.
- Still not phoneme-accurate lipsync; it remains a speaking-loop fallback until a true lipsync bridge is connected.
