## Root cause 真實 evidence

### Bug 1 · `with_ttl(int)` TypeError（已修 · 但只是表面）

publisher line 114（修前）：
```python
.with_ttl(int(duration_s) + 60)
```

livekit-api 1.1.0 預期 `timedelta`，不是 `int`：
```python
{'ok': False, 'detail': "renderer token mint fail: unsupported operand type(s) for +: 'datetime.datetime' and 'int'"}
```

同類 bug 在 `castle/server/livekit_endpoints.py` commit e750315 已修（用 `timedelta(seconds=ttl_s)`）。publisher 漏同步。修補後 token 正常 mint。

## Root cause 結論：Modal serverless container 跑 WebRTC publisher 架構不相容

`wait_pc_connection timed out` 不是 STUN 失敗、不是 token 失敗、不是 signaling 失敗（WebSocket signaling 顯然有通 · room 建起來了）。是 **peer connection 的 ICE / DTLS 完整握手沒完成**。

Modal serverless 的本質限制：
1. **無 stable inbound port** — serverless container 是 outbound-only model · 沒固定 public IP / port mapping
2. **NAT type 未知 / 不可控** — Modal infra 對 container 的 NAT 行為未公開
3. **無 TURN credentials 持久化** — 即使 force TURN over TCP，也需要 TURN server 跟 Modal container 雙向交換 candidates · serverless container lifetime 太短 + NAT 行為未明

LiveKit Cloud 預期 publisher 是：
- 跑在「VM / 持久 server / 自有機房」這類有穩定 ICE candidates 的環境
- 或跑在「browser」（client-side · 有完整 WebRTC stack）

**Modal serverless 不在這兩類**。

## 路 B 評估：LiveKit Agents framework 不解這個問題

LiveKit Agents（`livekit-agents` Python SDK）= 上層業務框架（LLM/STT/TTS/avatar 整合）+ 底層 WebRTC stack（livekit-rtc）。

底層 WebRTC stack **跟現在用的 livekit-rtc 0.22 是同一套**。Modal 不相容問題在底層、Agents framework 救不了。

LiveKit Agents 跑得通的環境例子（官方 quickstart）：
- 本機 Python（dev）
- Docker container 跑在 VM
- LiveKit Cloud 自己的 Agent Compute（付費 · 業界叫 LiveKit Agents Cloud）

**沒一個是 Modal serverless**。

## Verdict · 砍 Modal LiveKit publisher 架構

### 不是補丁能修
- 沒辦法在 publisher code 內 hack 解 Modal NAT 限制
- 沒辦法靠 livekit-agents 框架繞過底層 WebRTC stack 限制
- 持續撞同類牆 ≥ 2 次（4/28 OpenAI realtime backend + 5/25 LiveKit publisher）= v5.4.24 砍架構紀律觸發

### 3 條可行替代路徑

#### Path A · 不用 LiveKit · 回 Phase 1 client-side 路徑
- musetalk-poc 本來就有 `/idle_continuous` endpoint 推 JPEG bytes
- browser fetch streaming / WebSocket / SSE 直接 consume frames
- browser 自己畫 video（`<canvas>` / `<img>` 換圖 / MediaSource API）
- **優點**：完全不需要 server-side publisher · Modal 直接 stream 給 browser
- **缺點**：延遲 vs WebRTC 高（500ms-2s vs 100-300ms）· 雙向（user mic in）要另外 ws

#### Path B · LiveKit Cloud Agents Compute（付費託管）
- LiveKit Cloud 自家 agent runtime · 同公司產品保證相容
- 但要付費（pricing 沒公開、需要聯絡 sales）· Edward NT$1300 lesson 後不該再燒
- **不建議**

#### Path C · 持久 server 跑 publisher（Fly.io / Railway / 自家 VPS）
- 換 hosting · 寫 systemd / supervisord 跑 publisher
- 撐 long-running connection · 有穩定 NAT
- **缺點**：失去 Modal scale-to-zero · 月固定成本（Fly.io ~$5-10/月）· 多一個 deploy target

## 我推薦 · Path A（回 client-side · Phase 1 路徑）

理由：
1. **Phase 1 既有路徑 work** · `/idle_continuous` JPEG streaming 已驗過
2. **無新依賴 / 無新成本** · Modal 既有 musetalk-poc 直接用
3. **scale-to-zero 保留** · Edward 燒錢紀律
4. **client-side render 可以做到順 25fps** · MuseTalk 輸出 25fps · browser 用 RAF 對齊
5. **延遲可接受**：500ms-1s 的 client-side latency 對 voice-driven avatar 還行（avatar 本來就是 secondary visual · 不是 conferencing）

實作估時（Path A）：
- 移除 LiveKit publisher app code（保留 token endpoint 給 future restore）：1 hr
- browser side fetch streaming + canvas render：4-6 hr
- 雙向 mic in：另開 ws endpoint：2-3 hr
- **總 castle 估時 7-10 hr · A 模式（高頻 active）約 2-4 active hr**
