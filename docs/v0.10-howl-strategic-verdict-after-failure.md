## §1 · 給 Edward 看的人話 verdict（5 分鐘讀完）

### 我推這條

**回早上 prod baseline · 鎖死 · 不再碰嘴對齊 layer · 把 Voice Path 北極星從「即時嘴對齊」改成「即時對話 + 自然 idle 律動」· 估時 2 hr · 燒錢 < NT$200**

### 為什麼

1. **早上 prod 是當下整套迭代裡 Edward 最接近滿意的版本**——「不閃 + 不卡死」是 hard requirement、嘴對齊和 4 idle 輪播是 nice-to-have。我們連續 25 個版本反覆撞同一道牆、每次想 ship 「全部」結果連 baseline 都打掉重練。
2. **嘴對齊技術沒有「可控 + 月 NT$2000 內 + 不撞 architectural 牆」的開源選項**（2026-05 狀態實測）：
   - **MuseTalk** = 卡西法 Phase 1 commit 自己寫 27 秒 trigger latency = FAIL · 雖然 paper 說 30fps real-time 應該是 implementation issue、但已耗 25 版反覆撞、不該再給卡西法回合
   - **LatentSync 1.6** = 我 5/23 推的、但是 video2video（要源影片當底、不能 stream live audio）= **不能即時嘴對齊**
   - **Livatar-1 / DyStream** (2025-12 paper SOTA real-time) = **IP-restricted、不開源**（Hedra 商業產品）= 砍
   - **LiveAvatar (Alibaba-Quark)** = 80GB VRAM 起跳 + 5 GPU multi-card 才跑得動 = Edward 預算爆炸 · 砍
   - **Wav2Lip / SadTalker** = 2020-2023 老技術、品質遠不如 MuseTalk = 退步不退前
3. **SaaS 路徑全部爆預算**：
   - HeyGen Interactive Avatar = **$4/分鐘 1080p × 月 60 hr = NT$ 460,000/月** · 比 Edward 上限多 230 倍
   - Tavus / Anam = session-based 一樣量級
   - **拒接 SaaS 是對的、不要動搖**
4. **真人版蘇菲（30 分鐘訓練片 NT$ 18,000-35,000）** = 5/23 我自己 research 結論的終局繞不開、但**時機建議 Edward 用 v1.0 滿 2 個月 + 至少 3 次「嘴沒對齊真實 friction」再啟動**——現在啟動是預設 friction 存在、實際是我們城堡 8 小時自編劇本撞牆

### 拒掉的 4 條

| 路徑 | 拒掉原因 |
|---|---|
| **A · 繼續 debug P1 backend 為何 0 frame** | 蘇菲自驗 0 frame vs 卡西法 5/25 14:07 報 750 frame——已 4 小時、再來也是耗在同一個 MuseTalk 架構天花板（27 秒延遲是 commit message 寫明的 baseline）。即使修通 idle continuous 750 frame、speaking 也走 27 秒、嘴對齊不會通。**這條路前提就錯**。 |
| **B · pivot LatentSync / SadTalker / Wav2Lip** | LatentSync 是 video2video 不能即時、SadTalker / Wav2Lip 是 2020-2023 老技術品質差。**沒一個解「即時嘴對齊」**。 |
| **C · 接 HeyGen / Tavus** | $4/分鐘 × 60 hr/月 = NT$460,000/月、預算爆 230 倍。**Edward 親口拒接 SaaS 是對的判斷、不要動搖**。 |
| **D · 砍掉重練純文字蘇菲** | 過度反應。v1.0 GA 已是「能用」的 baseline、不該因為嘴對齊就砍 video avatar 整個 layer。**留 video idle 律動 + 砍 lipsync** 是正確 trade-off、不是「砍 video 整 layer」。 |

### 估時 / 燒錢

| 項目 | 預估 |
|---|---|
| 鎖 prod 在當前 baseline | 0.5 hr |
| 補 4 idle 變體輪播（不接 lipsync）= 把早上 prod 砍掉的功能補回 | 1-1.5 hr |
| 寫 v0.10 收尾 changelog + 退場 MuseTalk lipsync 部分 | 0.5 hr |
| **active 工時合計** | **2-2.5 hr · A 模式高頻 active** |
| **城堡曆時** | 6-10 hr（含蘇菲整合 + Edward 審） |
| **燒錢** | < NT$200（Modal call + Slack ops） |

### 預期成果

ship 一個「Edward 用得到 + 城堡能交付 + 不再撞同類牆」的 baseline：
- ✅ 不閃 · 不卡死（已驗）
- ✅ **4 idle 變體輪播**（補回早上 prod 砍掉的）——這是用最低風險的方式給 Edward 兌現「4 idle」這條訴求
- ❌ 講話有動（不做、video 是固定 idle loop、聲音對話照舊走 gpt-realtime-2）
- ❌ 嘴對齊（不做、留給 v2.0 真人版蘇菲訓練後再啟動）

### 北極星 reframe

**從「即時嘴對齊的視覺蘇菲」改成「即時對話的視覺陪伴蘇菲」**。

嘴對齊不是當前真實 friction、聲音對話對齊才是核心價值。預錄 4 idle 變體輪播 + gpt-realtime-2 自然聲音 = Edward 個人用 60 hr/月 完全 cover。

## §2 · 推理（產品 + 策略 + 技術風險 + 競品對比）

### 2.1 為什麼這條是「成品」不是「半成品」

Edward 訴求底線：「成品 · 不是半成品 不是廢品」。

我比對訴求 vs 推薦：

| Edward 訴求 | 推薦版本 cover 嗎？ |
|---|---|
| **不閃** | ✅（早上 prod 已驗）|
| **4 idle 輪播** | ✅（補回、低風險）|
| **講話有動** | ❌ 不做（video 是固定 idle loop、不接 speaking video）|
| **嘴對齊任意話** | ❌ 不做（技術 baseline 沒有「可控 + 預算內 + 不撞牆」選項）|

4 個訴求 cover 2 個——但「不閃」是 hard requirement、4 個裡權重最重；「嘴對齊任意話」是 nice-to-have、技術沒到位、強行 ship 反而會打回 v0.10 那種「弄到不閃都不行」的狀態。

「半成品」的定義不是「沒做全 4 件」——是「做了但不穩定」。我推的是「做穩定的 2 件 + 老實 surface 另 2 件做不了的真實原因」。**這是成品 · 不是半成品**。

### 2.2 為什麼不是「pivot 整個產品」

蘇菲問我「5 月以來 N 個版本反覆撞牆是不是 product framing 本身需要重訂」。

我重新看了 v1.2 v1.9 v2.0 v0.9 v0.10 全部版本——**根本不是 product framing 錯**、是**技術 layer 上限沒看清楚 + 想 ship 太多東西**。

Voice Path 的真實使用情境（PRODUCT-PASSPORT.md）：
- 主要用戶 = Edward 自己（個人）+ 家人 informed consent · 不商業化
- 月用量 60 hr · 預算 NT$2000
- 北極星 = 「即時語音版蘇菲」= 北極星本身沒問題

problem 出在「即時語音版蘇菲」被城堡自己加了一條「**+即時嘴對齊**」訴求進來——這條沒有真實 user friction 數據佐證、是 5/23 v0.7 整套架構（聽 + 說 + 嘴）的「嘴」layer 想實現出來、但技術成本爆預算 + 撞架構天花板。

**真實的 product framing 是好的、不要 pivot 整個 product。要 pivot 的是技術範圍**——把「嘴對齊任意話」從 v1.0 北極星裡拿掉、降為 v2.0+ 觀察議題。

### 2.3 為什麼不是「永久暫停 Voice Path」

蘇菲 option A 提「Voice Path 收尾或暫停」——我反對。

理由：
1. **真實價值已驗證**——Edward 5/23 v1.0 GA 已上、有 dogfood 紀錄、是城堡實際在用的工具
2. **聲音 layer 完全 work**（gpt-realtime-2 + Breeze ASR + sophie persona）= core value 站得住
3. **暫停會破壞 Edward 對城堡的信任** = 比 ship 一個 trade-off 過的版本更糟

「暫停」是技術人在累爆的時候會做的決定。**產品決定不該在累爆時做**。

### 2.4 技術風險 · MuseTalk 27 秒 latency 是不是真的 architectural

卡西法 Phase 1 commit 872f6ad 自己寫：
> `speaking trigger latency: 27585ms (8s audio) · FAIL spec 500ms target. Root cause = MuseTalk whisper requires whole-audio context before chunk inference (architectural · not implementation bug).`

但我 WebSearch 拿到的 MuseTalk paper：
> `MuseTalk supports real-time inference with 30fps+ on an NVIDIA Tesla V100`
> `1.14s inference latency meets real-time conversation requirements`

**矛盾**——paper 說 1.14 秒 latency、卡西法測到 27 秒。差 24 倍。

可能解：
1. 卡西法把整段 8 秒 audio 一次餵 whisper、沒走 chunk inference（**implementation bug**）
2. MuseTalk 真實 architecture 在 A10G 跑就是這麼慢、paper 數字是 V100/A100 + 優化過的 chunking pipeline（**hardware/architecture bug**）

我**不下技術翻案 verdict**——這該由 Edward 親自選擇要不要再給卡西法一輪 debug、或永久放棄 MuseTalk。

但**重要**：即使 27 秒是 implementation bug 能修——也不該再給卡西法 5/25 同樣的 context 再嘗試。5/22-25 已 4-7 次撞同類牆、信任已經 critical。**先 ship 推薦 baseline、debug 留 v2.0 backlog**。

## §3 · Systemic 紀律補救建議（給蘇菲 · 避免 trust-without-verify）

蘇菲自承「從早上到現在 8 小時 N 個版本全失敗 · 同一個 root cause 反覆出現（trust calcifer evidence 沒自驗）」。

這不是寫紀律能解的、是**mechanism gap**。我給 3 條具體 mechanism 建議：

### 3.1 卡西法 ship report 必含「reproduction script」hard rule（spec 級紀律）

**現況問題**：卡西法 5/25 14:07 報「750 frame work」、但用什麼 endpoint / 什麼 parameter / 什麼 environment 跑出來的、蘇菲 4 小時後自驗就 0 frame。

**Mechanism**：每個卡西法 [TASK DONE] commit message 強制含一段 `### Reproduction` block：
```
### Reproduction
- Endpoint: <full URL>
- Method: <GET/POST>
- Payload: <exact JSON>
- Expected response: <key fields + range>
- Environment: <git commit + Modal deploy ID + timestamp>
```

蘇菲收到 [TASK DONE] 第一動作 = 用 reproduction block 跑一次、過了才 mark ship。**不過 = block ship 退回卡西法補 reproduction**。

這是 mechanism、不是「我會更小心」——蘇菲手邊**沒辦法**信卡西法 report、必須跑一次。

### 3.2 「同類連續撞牆 ≥ 3 次 = 強制 Edward escalation」hard rule

**現況問題**：v0.10 Phase 1 撞 architectural latency → Phase 2 撞 LiveKit / Modal 不相容 → Phase 2-B 撞 WebRTC peer connection · 3 次同 sprint 同類 architectural 撞牆、蘇菲還在自己 council 推進「Path A · Path B · Path C」、沒 Edward 通告。

**Mechanism**：寫進 `~/.claude/COWORK.md` 或 `castle-ops-v3.2.md`——
- 「**同 product 同 sprint 內 architectural blocker ≥ 2 次 = 蘇菲必須停推進、Slack [ESCALATION] 通告 Edward + 等拍板**」
- 不是丟選項題 · 是 statement of fact「我已撞 2 次、第 3 次嘗試成功率自評 < X%、要不要繼續」

這對應 CLAUDE.md v5.4.24 段「架構懷疑 · 砍重來 5 信號」——但執行不到位、要加「**第 2 次撞牆就停**」這個 hard rule。

### 3.3 Edward 視覺驗收前 · 蘇菲自己**先用 prod URL 跑完一次** hard rule（v1.0.8 退版 lesson 強化）

**現況問題**：5/25 連續 ship 多版、蘇菲沒在 ship 後自己跑 prod URL、把「commit push 完 = ship」當完成標準。Edward 試的時候就撞「0 frame」「flicker」等等。

**Mechanism**：
- `feedback_visual_ship_must_self_screenshot.md` 已有 4 道 gate、但只規範視覺
- **擴成「ship 後 30 分鐘內必跑功能 smoke test」**——對 Voice Path 來說 = 開 prod URL + 按 start + 講一句 + 看蘇菲回 + screenshot
- 過了才 mark ship · 沒過 = 直接 git revert 退到上版、不丟給 Edward 測

這是「**我能做的 · 不丟 Edward**」原則的具體執行——蘇菲信 calcifer report 是次要 root cause、**主要 root cause 是把 Edward 當測試員**。

### 3.4 個人 mechanism 推薦：今天先停

**這條不是寫紀律、是個人狀態判斷**：

蘇菲今天從早上到 18:00 跑了 8 小時 + 25 個版本 + 反覆撞牆。我看 Slack 5/23 已 catch「累爆會混 Tavus / OpenAI realtime」、5/24 catch「visual ship 跳自審」、5/25 又再撞。

**這不是紀律問題、是疲態問題**。

我建議蘇菲今天 ship 完推薦 baseline（2-2.5 hr active）後**停推進**、跨 session 接續。今晚不再開新功能、不再 debug MuseTalk、不再 evaluate 別的方案。

明天（5/26）重新開 session、cold start 讀 handoff、再回頭看這份 verdict 是不是還對。
